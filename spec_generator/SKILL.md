# 通用实现 SPEC 生成

把需求、概要设计和项目事实细化为可编码、可测试、可追溯的中文 Markdown 实现规格。沿用原 Gmall SPEC 的方法级深度，将框架、数据存储、目录和日志约定交由目标项目决定。

## 调用与范围

仅在用户手动调用时使用。生成或调整文档不代表获得业务实现、安装依赖、执行迁移或部署的授权。用户已指定输出结构、技术栈和范围时优先采用。

## 输入与证据

1. 读取用户提供的需求、模块概要设计、系统约定、相关接口和关联模块 SPEC。已有项目同时核实目录、入口、数据对象、实际调用方及测试；只读取与目标模块有关的文件。
2. 建立输入表，标注来源路径、版本（可得时）与用途。区分“已验证现状”“已确认需求”“设计提案”“待确认”。需求与现有实现冲突时明确列出差异。
3. 缺少独立 PRD 或概要设计时，可基于已有材料产出草稿。仅对影响核心契约、权限或模块边界且无法合理推断的决策提问；其余缺口列入待确认表并说明影响。
4. 现有符号用核实后的名称；新增文件和符号给出具体建议名称并标注“拟新增”。不得把建议路径写成已存在事实。

## 生成流程

1. 明确模块目标、范围外事项、上下游、输入输出和需求编号。已有编号保持稳定。
2. 识别技术栈、分层、存储、通信方式和项目规范。没有选定技术栈时使用逻辑组件与类型描述，把框架绑定细节列为待确认。
3. 读取 [SPEC 模板](assets/spec-template.md)，按适用性展开。无前端、无数据库、无 HTTP 的模块不强加对应设计，注明不适用原因。
4. 先定义数据与对外契约，再细化文件、函数或方法、交互和失败分支。每个公开操作覆盖参数来源、类型、约束、返回、关键步骤、副作用、错误和依赖；复杂逻辑补充伪代码。
5. 将验收条目映射到需求、方法或接口，补齐实际相关的并发、重试、权限和恢复行为。具体性能数值需有来源，建议目标须明确标注。
6. 使用 [质量检查](references/quality-checklist.md) 检查跨章节一致性，并修复可自行解决的冲突。
7. 输出到用户指定位置；否则沿用项目文档目录；无约定时使用 `docs/specs/<module>/spec.md`。已有文件先读取并保留无关内容。交付说明路径、状态、主要待确认项及实际执行的检查。

## 技术适配

- 数据存储：关系型数据库写字段、主键、索引、唯一性、外键策略、事务和迁移。确定数据库及版本后给出适配的 DDL 或项目迁移格式；已有表给出增量变更。不预设自增 ID、软删除或禁用索引。非关系型存储描述对应 schema、访问模式与一致性。
- 业务逻辑：沿用项目模块与依赖方向，可使用函数、服务、组件、任务或节点。按实际框架描述注解、中间件和序列化，不强制 Controller/Service/Mapper。
- 界面：按实际 UI 技术描述状态、组件、事件、校验、加载/空/失败状态和接口映射；展示字段与传输字段分别定义。
- 契约：覆盖实际使用的 HTTP、事件、流、CLI 或内部函数。示例完整展示所定义对象，分页、可空、缺省、时间、枚举和错误语义保持一致。
- Agent/RAG：适用时定义状态 schema、节点输入输出、工具权限、检索与证据契约、退出条件、超时/预算、失败与评测样例。
- 可观测性：按业务事件定义级别、字段、关联 ID 和脱敏。不要求每层重复记录请求全文或在前端输出所有请求。

## 输出标准

标题、表格和代码块使用标准 Markdown；描述默认中文，技术标识保留原名。使用可执行的验收条件，避免“正常运行”“性能良好”。草稿允许明确的待确认项，但存在阻断实现的未决契约时不得标为“可实施”。Spec 是实现依据，检查通过不代表实现或测试通过。
