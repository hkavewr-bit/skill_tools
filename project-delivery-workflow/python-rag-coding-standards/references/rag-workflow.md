# RAG / 工作流编码规则

这些规则由源项目组织方式与静态观察提炼；关于一致性、并发和失败处理的强化要求是改进建议，不能据此声称源项目已经实现。

## 节点与编排

- 沿用 `NodeBase.__call__()` 包装执行、`process()` 实现业务的模式。包装器统一处理日志、计时和任务事件，业务节点不重复包装。
- 节点只负责一个可命名阶段：解析、切分、向量化、召回、融合、重排或生成。外部 SDK 细节放入专用适配器。
- 节点 ID、实例属性、`name` 和任务展示映射保持可追溯；中文展示名称不要参与路由判断。
- 编排类分开创建节点、注册节点和注册边；路由函数返回的目标必须已注册。编译复用不得泄漏不同请求的可变状态。
- 新增节点前检查基类构造参数与调用方式。源项目存在两份基类，不可凭文件名猜测继承契约。

## 状态与数据流

- 状态字段写出具体类型与阶段语义。初始必需字段与中间字段分别定义；使用可选字段时，消费前检查可用性，不能以 `total=False` 替代校验。
- 新节点优先返回自己产生的字段更新；在目标框架确认其合并语义。不要直接修改共享输入中的嵌套列表或字典。
- 维护已有全量返回节点时检查相关边和消费者后再变更，不在局部任务中无依据重写整个图。
- 并行分支明确每个字段的写入者；同一字段多写入者须有适合业务语义的合并规则。汇合节点的依赖完成条件应按实际框架版本验证，不能仅凭图形判断。

## 检索与模型适配

- 在融合或重排前规范化各来源数据，明确正文、标题、文档/切片 ID、来源、URL 和分数语义。数据库外层包装不应无约定地泄漏给后续节点。
- 去重键必须稳定且非空。空 ID、空正文与缺失 `entity` 的处理明确，不能把多个缺失 ID 的文档误合并。
- 向量批处理保持输入顺序，核对文本数、稠密向量数、稀疏向量数和维度。返回结果不等长应显式失败或采用已定义策略。
- 重排分数与文档按明确索引匹配，避免 `zip` 静默丢失尾部数据。排序方向、Top-K 范围和阈值来自配置或有依据的业务约定。
- 模型返回先解析校验，再进入内部契约；JSON 字符串、Python 字典和 Pydantic 对象分别处理。
- 外部失败与“成功但无结果”分开处理。降级返回应保持消费者期待的列表/对象结构，并保留可识别的失败或降级状态。

## Web、后台任务与 SSE

- Web 入口负责请求模型、校验、任务创建、业务调用和响应映射。长耗时流程交由适合运行环境的执行机制，不在异步处理器中直接执行阻塞计算或同步网络调用。
- `session_id` 表示会话，`task_id` 表示一次执行；同会话并发请求应能独立追踪。
- 任务接受、运行、完成与失败分别表达；接收成功不等于工作流完成。节点“结束”与业务“成功”不是同一状态。
- 流式执行器返回惰性迭代器时，必须消费迭代器才能驱动工作；定义提前停止、取消和错误传播行为。
- 沿用集中事件常量及结构化 payload 的方式，明确定义进度、增量、最终结果、错误事件；终止、断连、等待超时和清理路径完整。
- 队列使用符合线程/事件循环边界的投递机制；`put_nowait` 不能作为跨线程安全性的依据。明确容量、背压及是否丢弃事件。
- 进程内任务字典和队列仅在明确的单进程约束下使用；部署扩展时再选择共享状态/消息机制，不自动引入基础设施。
- 上传文件校验类型、大小、路径和目标目录；对象存储键包含足以避免覆盖的标识。依赖上传失败后的继续/中止策略须与业务契约一致。

## 相关验证点

优先验证真实的不变量：节点只更新预期字段、输入不被意外修改；路由均可到达；批结果等长；降级形状一致；同会话并发任务互不覆盖；失败状态不被成功覆盖；SSE 能结束并释放资源。完整流程联调需要实际依赖，不能用静态检查代替。
