# SPEC 交付检查

检查文档的实际内容，不只确认标题存在。把无法解决的问题带入未决事项表。

## 来源与范围

- 输入来源可定位；需求、现状、提案和待确认项清楚区分。
- 已有符号和路径经过核实，拟新增内容有明确标记。
- 每条范围内需求映射实现单元、接口或流程及验收条目。
- 技术栈与项目一致；无适用依据的前端、关系数据库或框架章节已裁剪。

## 可实现性

- 方法参数、返回、校验、步骤、错误和副作用足以实现。
- 实际调用方与提供方对类型、可空、默认值、枚举和错误理解一致。
- 数据库约束能支撑声明的唯一性和并发语义；无约束时说明替代机制。
- DDL/迁移适配选定数据库；变更说明存量数据、兼容和回滚限制。
- UI 状态、请求参数和展示字段有明确映射，展示文本不会冒充传输类型。
- 适用的事务、超时、重试、幂等和失败恢复具有清晰边界。
- Agent 适用时：状态读写、工具输入输出、证据引用、终止条件及评测可追溯。

## 跨章节一致性

- 同一字段在模型、方法、数据库和契约中类型及含义一致。
- 同一操作的名称、路径、错误码、权限和状态转换各处一致。
- 请求响应示例完整且符合定义，示例中的唯一性、范围和引用条件成立。
- 日志设计可定位关键失败且明确敏感字段处理。
- 验收覆盖需求和关键失败分支，结果可观察且没有虚构测试通过记录。

## 状态与交付

- 已删除模板指引；未决问题集中列出影响和是否阻断。
- 核心契约未决时保持草稿/待确认状态。
- 文件已保存，引用路径可定位；交付说明记录实际完成的检查。

## 常见偏差

| 偏差 | 修正 |
|---|---|
| 把领域名称替换后仍保留固定框架分层 | 从目标项目入口、调用关系和依赖重新确定实现单元 |
| 为了填满章节虚构数据库或页面 | 标注不适用，并展开实际存在的边界 |
| “真实命名”被理解为可以编造现有符号 | 区分已核实符号与拟新增符号 |
| 每个方法都打印完整输入输出 | 按业务事件设计日志，并明确脱敏与排除字段 |
| 规格中写出成功场景就声称验收通过 | 分开预期结果和实际验证证据 |
