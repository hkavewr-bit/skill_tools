# 业务流程与 PRD

使用用户已有目标、会议纪要、交流、截图及代码事实直接形成草案。标注来源位置，区分明确需求、竞品观察、AI 建议和待确认项；截图不能证明后台规则，代码现状也不是已批准需求。流程图与 PRD 可同时起草，按以下顺序确认。

## 业务流程

对齐角色、触发、正常路径、分支、异常、结果和版本边界。通过[工具协作](tools.md)生成可编辑业务图并展示实际渲染；使用[流程模板](../assets/templates/business-flow.md)保存 `业务流程图.md`。图先表达业务，不锁定技术实现。用户确认当前流程版本后进入 PRD 终审过程。

## 详细需求

用 [PRD 模板](../assets/templates/prd.md)按业务模块整理：目标与前提、输入输出、规则、权限/数据范围、失败与恢复、优先级、依赖和可观察验收。保留核心用户旅程及当前版本明确不做的内容，非关键需求可明确延期。

同时对齐适用的容量、延迟、并发、成本、数据保留，以及目标系统、资源/GPU、网络、外部服务和可用测试环境；未知项标明影响。Agent 项目补[评测要求](agent-evaluation.md)。

优先提出影响实现的未决问题；已有材料足以决定的内容直接复用。按模块确认，再核对业务图与全部当前需求一致，展示整份 PRD 的范围和关键决定进行终审。关键业务歧义解决、用户确认 PRD 版本后进入实体设计。
