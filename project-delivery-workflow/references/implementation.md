# 小步实现、验证和验收

## 进入条件

当前交付版本的 PRD、适用的前端设计、总体架构及全部模块 Spec 已确认，骨架已建立，跨模块检查通过。检查进度记录对应当前实际版本后开始。纯后端不等待前端不适用阶段。

## 一个切片的闭环

1. 读取关联需求、Spec、当前代码和任务边界，解释本次可展示的业务结果。
2. 为真实业务行为编写有意义的验证：正常、边界、异常及权限/状态变更。新功能和缺陷按适用测试驱动规范推进，避免用匹配源文件文字的测试证明业务正确。
3. 在允许范围实现；保留无关修改，修复根因。调用审查技能检查需求符合性和代码质量，审查者指出问题需核实。
4. 执行相关测试、契约/集成测试、必要的构建或类型检查；遇到失败修复后回归，避免没有新原因反复跑全套。
5. 同步受影响文档和进度，报告真实命令、环境、结果、未测项。
6. 演示完整业务行为，提交用户验收。验收通过后进入下一个切片；失败则修复本切片。

内部辅助函数、重命名或格式调整无需独立人工验收。若它们改变了已批准的公共行为/边界，走受影响范围的重新确认。用户明确授权批量验收时，记录其范围，避免无授权跳过或重复审批。

## 测试边界

开发验证可以运行项目测试、构建和授权范围内的临时应用测试进程，但不代表可启动最终部署环境。不得为验收自动运行部署 Compose、安装数据库服务或执行部署初始化。

外部集成优先使用用户已提供/已授权的测试环境和合成数据。环境不足时执行不依赖它的单元/契约测试，明确真实联调受阻；模拟服务通过不等于真实联调通过。需要额外环境权限时，说明影响并请求最小必要输入或授权。

测试报告区分：通过、失败、受阻、未执行、不适用。仅有静态检查不算功能已验证；日志存在不代表结果正确。

Agent 项目读 [效果评测](agent-evaluation.md)，代码测试与真实模型效果分别报告。

## 整体验收

逐项对照当前 PRD 验收标准和总体设计的需求映射，检查跨模块业务链路、适用的权限/异常/重复操作/恢复场景。补齐功能修复与相关回归，检查文档及使用说明一致。

用户验收结论针对具体版本。必要外部测试受阻时，不把整体验收标为全部通过：列出证据、剩余项和是否请求用户接受明确例外。只有确有用户接受才记录“有条件验收”。

完成后转入部署资料交付。源码完成、验证通过、用户验收和部署运行是四个不同状态。
