# 状态、文档与变更

仅在初始化、恢复差异或变更时读。`user_workspace/` 是项目产物目录，不是第二个代码仓库；按需生成文档，不一次创建全部空壳。已有文件先读再合并。

## 唯一来源与位置

| 产物 | 路径/职责 |
|---|---|
| PRD、业务图 | `PRD.md`、`业务流程图.md`；业务范围与路径 |
| 逻辑实体 | `数据实体.md`；小项目可合入总体设计并登记唯一位置 |
| 总体设计 | `总体设计.md`；概要/定稿共用，维护需求→模块/接口→Spec→验证映射 |
| 前端 | `frontend/` 下实际工具源文件、交互设计、前端设计规范；文件名以工具为准 |
| 模块 | `modules/<模块名>/spec.md`；物理存储、接口和主要函数契约 |
| 状态、证据 | `项目进度.md`、`测试报告.md`；确认和验证分别记录 |

模板由各阶段参考直接链接；初始化进度用[进度模板](../assets/templates/progress.md)。文档注明具体版本与上游基线，语义变化递增版本；确认记录只在进度维护，其他文档引用。PRD 用稳定需求编号，技术模块不必与业务模块一一对应。

进度分别记录设计状态（草稿/待确认/已确认/受影响待重审）、实施状态（未开始/实现中/已验证/受阻）、验收状态（待验收/已验收/有条件验收）和交付状态。验收以模块及整体版本记录，功能流表只记开发验证；不要把“PR 已更新”当设计或验收状态。

## 恢复

核对项目/分支、确认依据、相关实际文件与测试证据。进度记录不能证明文件没变；对差异列影响，仅使相关下游项待重审。已有对话可证明的确认直接补录，无法核实则标待确认，不捏造回复或时间。从首个未满足步骤继续，不重新采访已确定内容。

## 变更分类

| 变化 | 处理 |
|---|---|
| 业务范围、规则、验收 | 更新受影响 PRD/业务图、实体和设计，确认后编写依赖它的业务代码 |
| 职责、公共契约、存储结构 | 更新总体设计、拥有方及消费者 Spec、字段映射与测试，确认受影响范围 |
| 内部实现，公共行为未变 | 已授权范围内直接推进，按实际影响同步 Spec 并回归，不逐辅助函数审批 |
| 格式或无语义文档修正 | 保留语义批准，注明无语义变化；无关文档不无故升版 |

每次变更核对需求、实体、原型/接口、函数、测试和使用说明的受影响链路。流程/范围/交付方式被用户明确替代时记录依据；催进度本身不是替代决定。
