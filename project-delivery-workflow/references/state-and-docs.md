# 状态与文档维护

## 项目产物位置

初始化即建立文档根目录；此时不需要建立业务代码骨架。先读现有文件再合并更新。

```text
user_workspace/
  PRD.md
  总体设计.md
  业务流程图.md
  项目进度.md
  测试报告.md
  frontend/                   # 仅有前端时创建
    页面设计.pen
    交互设计.md
  modules/
    模块名/
      spec.md
```

实际前端文件扩展名/名称以设计工具为准；在总体设计中记录真实可编辑文件及预览路径，不制造不存在的文件链接。README、Dockerfile、Compose 和数据库脚本属于项目运行交付物，放项目根目录或既有工程目录，在总体设计/README 中链接。

## 模板路由

模板是生成文档的框架，不是已完成需求。仅复制当前阶段所需模板，替换提示，空白内容标“待确认”，不一次生成全部空壳文档。

- 业务探索：[业务流程模板](../assets/templates/business-flow.md)
- 详细需求：[PRD 模板](../assets/templates/prd.md)

## 一个进度来源

`项目进度.md` 是阶段、确认和下一步的入口。模块任务可以放各 Spec 中，但在进度表链接，不复制两份任务完成状态。状态必须区分：草稿、待确认、已确认、实现中、已验证、待验收、已验收、受影响待重审、受阻。

文档版本使用项目内明确的版本标识。每次实质修改递增并记录摘要；审批记录包含对象/版本、用户明确回复的时间或会话位置、确认范围。必要时附内容哈希或 Git 版本以核对。不要捏造用户原话或时间；无法核实则写待确认。

“设计已确认”“代码测试通过”“用户验收通过”是不同事实。批准业务切片不能自动批准整个项目或部署。

## 恢复流程

1. 定位正确项目/分支，读取项目说明、进度和本次相关文档。
2. 比较确认版本与当前文件，查看现有修改和相关测试证据；进度文本不是当前文件正确的证明。
3. 对已确认但已变更的内容列差异，仅使受影响模块/下游项进入待重审。未受影响的批准保留。
4. 从第一个未满足的阶段/切片恢复。没有确认记录时先搜已有对话证据，仍无证据才提出聚焦确认。
5. 报告当前可继续的下一步，不重新采访已确定且未变化的需求。

## 变更闭环

先判断变化属于业务需求、公共契约、内部实现还是纯文档修正。

- 业务规则/范围/验收改变：列影响，更新 PRD/业务流程草案及关联设计，提交用户确认后改代码。
- 模块职责、跨模块函数契约、持久化结构改变：更新总体设计、涉及的 Spec 与测试标准，按影响范围确认。
- 只改变内部实现且不影响已批准行为：在授权开发内推进，更新受影响的 Spec 并回归；不要求逐辅助函数批准。
- 不相关的文档只核对，不做无意义版本变更；格式修正可沿用语义批准并标明无语义变化。

每次代码变更后检查：需求—设计—函数契约—测试—使用说明是否一致。文档更新与功能交付属于同一个完成条件。

## 需求追踪

PRD 以业务功能编号（如 FR-001），技术模块使用稳定模块名。总体设计维护“需求 → 模块/接口 → Spec → 测试/验收”的关系。一项需求可以跨多个技术模块；不强迫业务模块与代码目录一一对应。
