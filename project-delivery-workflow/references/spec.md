# 模块 Spec、契约检查与切片

输入：当前确认的 PRD、实体、总体设计、适用前端产物及已验证骨架。按技术模块依赖顺序用[模块模板](../assets/templates/module-spec.md)编写 `modules/<模块名>/spec.md`，包括本版本前端与 Agent 编排模块。

## 编写与确认

Spec 以模块组织，至少包含模板中的七项：目标、页面、实体、接口、规则、文件、验收；规则内附主要函数契约。字段、示例和契约细节直接按模板填写，本参考不另列一份重复清单。

共享逻辑实体引用权威位置和版本；模块拥有的物理模型与对外契约在该 Spec 定义，消费者写明映射和依赖版本。没有页面或 HTTP 时标不适用，按函数、事件、任务等真实调用方式定义，不能省略模块的输入输出。

对业务决策密集的主要函数补步骤/伪代码；不预写完整实现，也不为每个 getter、回调或私有辅助函数单独审批。详略以能否明确编码和验证为准。依赖假设、建议及未决项显式列出，不能用一个模块的确认批准未讨论的下游规则。

按模块展示并确认具体版本，执行入口的全部 Spec 门槛。

## 跨模块检查

在总体设计记录检查依据、结果与问题。此时检查计划验收场景及观察方法，实际测试证据在实施后补入：

- 调用双方字段、类型、空值、错误、版本及同步/异步语义匹配。
- 数据写入、事务、状态、缓存、事件归属与重复请求行为一致。
- 依赖无意外环路，真正服务边界执行权限检查。
- 每条当前需求有完整业务及失败/超时/恢复链路，覆盖前端、后台、外部服务与 Agent。
- 原型字段/按钮可追溯到实体、DTO、接口或本地行为；文件规划符合骨架，验收能观察结果。

发现冲突按[变更规则](state-and-docs.md)修订并确认受影响内容；关键问题解决、全部当前 Spec 确认后检查通过。

## 拆分业务切片

将可运行的端到端业务结果写入进度的切片表，填需求、涉及模块、修改范围、禁止破坏项、预期行为、测试、文档影响与演示方式。切片可横跨模块，不按技术层整批实现。需要计划能力时读[工具协作](tools.md)。

每个切片对应完整可执行功能流，标明主责模块及依赖；模块功能流全部完成后安排 Spec 集中测试验收。模块归入业务阶段，阶段所含模块验收后再做质量检查。队列与验证粒度见[实施](implementation.md)，不为内部函数另拆测试任务。
