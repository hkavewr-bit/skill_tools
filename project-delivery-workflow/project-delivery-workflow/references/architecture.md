# 总体架构、骨架、模块 Spec

## 1. 简洁总体设计

输入：PRD 确认基线、业务流程；有前端时还需排版和交互确认基线。提出足够简单的整体方案：模块职责/边界、依赖方向、核心数据及接口、后台能力、技术选择的理由和部署约束。

用总体架构图在 Visual Companion 展示并迭代，源图保存在总体设计中或由其链接。以业务链路验证模块完整性，不凭习惯引入微服务、消息队列或多 Agent。

覆盖适用的身份/授权、事务、幂等、异步任务、超时/重试、日志追踪、数据持久化与外部集成。按项目风险选择细节，明确不适用项。总体设计不展开所有内部函数。

交接：用户确认总体方案、当前版本技术模块清单与依赖顺序。

## 2. 建立基础骨架

在确认范围内建立目录、应用入口、配置示例、依赖清单、测试框架与必要开发工具。基础启动/健康检查可验证，不实现登录、检索等业务用例。目录不等于功能完成，未实现业务不提供假的成功返回。

基于实际项目条件进行基础运行检查。不能以骨架验证为理由启动部署 Compose 或安装外部数据库服务；权限/环境不足时记录具体阻碍。

## 3. 依赖顺序编写模块 Spec

为当前交付版本所有技术模块建立 `modules/<模块名>/spec.md`，使用 [模块模板](../assets/templates/module-spec.md)。包括前端在范围内的技术模块及 Agent 编排模块。按依赖顺序逐模块与用户对齐，而不是先实现第一个确认模块。

每个主要函数明确：名称/签名草案、职责、输入类型与约束、输出契约、错误、数据变化/副作用、依赖和测试标准。对业务决策密集函数补充算法步骤/伪代码；不预写完整实现或锁死所有私有辅助函数。

数据库模型、接口字段、状态机、权限边界归到明确模块，并被总体设计引用；共享契约只维护一个权威定义。每个模块标出来自其他模块的假设。模块确认不能批准尚未讨论的下游假设。

用户逐模块确认后登记版本。当前版本全部 Spec 完成前，不进行业务代码开发；用设计产物、契约示例和基础骨架展示进度。

## 4. 跨模块检查

检查并记录：

1. 调用方/被调用方的字段、类型、空值、错误和同步/异步语义匹配。
2. 数据写入、事务/状态更新、缓存和事件归属明确，重复请求行为一致。
3. 没有意外循环依赖；鉴权与权限验证在真正的服务边界落实。
4. 每个当前 PRD 需求都能沿完整业务流程经过相关模块并得到验收证据。
5. 前端、后台任务、外部服务与 Agent 的超时/失败/恢复路径可衔接。

发现问题修订受影响 Spec；必要时回到总体架构/PRD 并重新确认受影响版本。关键问题解决、全部当前 Spec 确认后才通过此阶段。

## 5. 任务拆分

用 writing-plans 能力把工作拆成可运行的业务切片。任务清单放项目进度，每项记录需求编号、涉及模块、允许修改范围、不得破坏的行为、预期行为、测试、文档影响与验收演示。切片可横跨模块，不按“先写完所有数据库层”拆分。

实施队列的 WIP 上限为 1。只有一个切片可标记“实现中”；它完成验证和文档同步后自动更新当前版本 PR，用户验收通过后才能领取下一个切片。

把相关业务切片归入明确的业务阶段，并在拆分时为每个阶段安排一个质量检查点。检查点位于该阶段最后一个切片验收之后、下一阶段开始之前，包含模块职责与依赖复核、必要重构、完整回归和文档一致性检查；不借质量整理扩展新功能。

## 技术可行性探测

外部模型、协议或基础设施能力不确定且会影响方案时，先向用户说明待验证问题、最小范围、成本及可能副作用；获准后隔离验证，记录事实与未验证项。结果更新设计。探测不隐含业务开发、服务部署或生产数据写入授权。
