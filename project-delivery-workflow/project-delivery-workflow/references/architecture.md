# 总体设计与基础骨架

用[总体设计模板](../assets/templates/architecture.md)维护同一份 `总体设计.md`。概要方向与架构定稿是该文档的两个阶段，复用未变化的决定。

## 概要方向

PRD 和逻辑实体确认后，多子系统、复杂权限/状态、外部集成或明显技术风险的项目先确认系统边界、技术方向、主要组成、业务/数据流、依赖及运行约束。简单项目可合入架构定稿，在进度记录理由。

原型前不锁定后端 URL、DTO 或内部函数。概要供页面和 Spec 定方向，详细接口在后续阶段确定。

## 架构定稿

有前端时基于已确认布局、交互与规范；无前端时基于 PRD、实体和业务图。明确当前版本技术模块、职责、依赖、数据归属、公共契约归属及需求映射。按实际风险覆盖身份/权限、事务/幂等、异步、超时/重试、日志、持久化和外部集成。

记录跨切片不变量及禁止破坏项；用完整业务链路核对前台与后台能力，不凭习惯加入微服务、消息队列或多 Agent。经[工具协作](tools.md)展示可编辑架构图，确认方案、模块清单和依赖顺序后建立骨架。

## 基础骨架

仅建立已确认架构中的目录、入口、配置示例、依赖清单及测试框架，执行可用的基础启动/健康检查。不实现登录、检索等业务用例，不返回虚假业务成功。环境不足时记录具体阻碍，运行边界见[交付](delivery.md)。骨架验证后进入模块 Spec。

## 技术可行性探测

不确定技术阻碍设计时，明确问题、最小范围、成本和副作用；已有授权覆盖的只读调查或可逆隔离验证可直接做，超出授权的外部调用/写入再请求必要授权。结果回写设计；探测不代替业务编码门槛，也不扩展为部署。
