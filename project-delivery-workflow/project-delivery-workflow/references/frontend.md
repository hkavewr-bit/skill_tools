# 前端：先排版，再交互

输入：已确认的当前版本 PRD、业务流程、目标设备与设计约束。无前端时记录不适用并跳过，不生成虚构页面。

## 第一步：排版

确认 pen.dev 连接器实际可用，并按该工具文档操作。围绕页面清单、导航层级、内容区域、视觉层级、表格/表单位置生成可编辑设计稿。先展示一个代表页面，再按一致风格完成范围内页面。

本轮只确认页面布局。示例内容标明示例，不把它变成新增业务承诺。尚未讨论的权限/异常交互留到下一阶段，不一次塞满状态设计。

保存到 `user_workspace/frontend/` 或用户已有的明确文件位置，记录设计源文件、预览和版本。验证实际保存结果；工具缺少保存能力时如实提出所需最小用户动作，不把内存画布说成已落盘文件。

用户确认排版版本后进入交互设计。

## 第二步：交互

逐页面/业务流程说明用户操作、跳转、字段校验、提交反馈、加载/空/失败状态、权限差异、数据需求。适用时覆盖取消、重复提交、流式回复停止和恢复。

产出 `frontend/交互设计.md`，关联页面设计节点、PRD 需求和待设计接口。这里描述需要什么数据与行为，后端的正式接口契约在总体架构/Spec 阶段确定。

页面设计引入新业务动作时，更新 PRD 和业务流程并确认受影响部分，不能只加一个页面按钮。全部当前交互确认后再做后端模块与整体技术架构。

## 第三步：提炼前端设计规范

排版和交互确认后，使用 [前端设计规范模板](../assets/templates/frontend-design.md) 生成 `frontend/前端设计规范.md`。规范必须来自已确认页面，不在页面确认前凭空锁定完整设计系统。

记录适用的颜色、字体、间距、栅格、响应式规则、组件复用方式，以及 Hover、Focus、Disabled、Selected、加载、空状态、失败和无权限等视觉表现。维护“已确认页面 → 通用组件/规则”的对应关系，并明确当前版本不得随意改变的视觉规则。

只把跨页面复用且已经确认的规则提升为规范；单页特例保留在页面或交互说明中。页面后续变化影响公共规则时，同步更新规范并重新确认受影响部分。

## 交接

带入总体架构的内容：已确认 PRD、业务图、布局版本、交互版本、前端设计规范版本、页面数据与操作需求。页面需求只是一部分；后台定时任务、异步处理、Agent 状态恢复和权限校验仍需根据 PRD 检查。
